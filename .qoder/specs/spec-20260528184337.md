# Module 1.6 — 反馈与系统参数实体 实现计划

## Context

根据 `basketball-match-platform-specs.md`，Module 1.6 是 Phase 1（数据层）的最后一个模块，依赖 Module 1.5（比赛与群聊实体）已完成。本模块需要定义赛后反馈、系统参数、通知三个领域的实体，并创建对应的 Migration 文件和种子数据。

已有的代码库模式（从 Module 1.1-1.5 总结）：
- 实体使用 TypeORM 装饰器，`@PrimaryGeneratedColumn('increment', { type: 'bigint' })` 为主键
- 列名使用 snake_case 通过 `name` 属性映射
- 枚举类型定义在 `shared/types/` 中，以 `const` 数组 + 派生 union type 的形式
- 实体类上有 `@Index` 和 `@Check` 装饰器
- Migration 使用原生 SQL，ENUM 创建使用 `DO $$ EXCEPTION` 保证幂等性
- 测试使用真实 PostgreSQL 连接，`synchronize: true` 自动建表，通过 `information_schema` 验证结构
- 每个实体有对应的 `.spec.ts` 测试文件
- 种子数据通过独立的 Migration 文件插入

## 实现计划

### Step 1: 创建共享类型（shared/types/feedback.ts, shared/types/notification.ts, shared/types/system.ts）

定义以下常量数组和类型：

- `LEVEL_MATCH_OPTIONS = ['unclear', 'lower', 'equal', 'higher'] as const`

**shared/types/notification.ts:**

**shared/types/system.ts:**

- **P0 关键补全**：为每个键定义对应的 TypeScript JSON 数据结构接口：
  - `AbilityAdjustWeights` — 能力匹配调节值权重结构
  - `MatchThresholdParams` — 动态阈值参数结构
  - `BaseAbilityWeights` — 基础能力值计算权重结构
- 提供 `SystemParamValueMap` 映射类型，将 `SystemParamKey` 映射到对应接口

更新 `shared/types/index.ts` 导出新增模块。

### Step 2: 创建实体文件（TDD: 先写测试，再写实体）

**server/src/modules/feedbacks/entities/feedback.entity.ts**
- 表名: `feedbacks`
- 字段: `id` (bigint PK), `match_id` (bigint, FK → matches), `player_id` (bigint, FK → players), `overall_rating` (int, CHECK 1-5), `overall_reason` (varchar 500, nullable), `submitted_at` (timestamptz, DEFAULT now()), `region_code` (varchar 20, nullable)
- 唯一约束: `(match_id, player_id)` — 每场比赛每球员只能反馈一次
- 索引: `match_id`, `player_id`
- 关系: `@ManyToOne` → Match, `@ManyToOne` → Player

**server/src/modules/feedbacks/entities/feedback-player-rating.entity.ts**
- 表名: `feedback_player_ratings`
- 字段: `id` (bigint PK), `feedback_id` (bigint, FK → feedbacks, ON DELETE CASCADE), `rated_player_id` (bigint, FK → players), `level_match` (enum: unclear/lower/equal/higher), `sportsmanship` (enum: good/average/poor), `action_cleanliness` (enum: clean/average/dirty), `is_punctual` (boolean, nullable), `created_at` (timestamptz, DEFAULT now())
- **P1 业务约束**：Migration 中增加 CHECK 约束禁止自评。由于 PostgreSQL CHECK 不支持跨表子查询，采用触发器或应用层校验。计划选择**应用层校验**（在 FeedbackService 中实现），同时在实体文档中明确标注此业务规则，保持数据库层简洁。
- 关系: `@ManyToOne` → Feedback, `@ManyToOne` → Player (rated_player)

**server/src/modules/system/entities/system-param.entity.ts**
- 表名: `system_params`
- 字段: `id` (bigint PK), `param_key` (varchar 100, UNIQUE, NOT NULL), `param_value` (JSONB, NOT NULL), `description` (varchar 255, nullable), `updated_at` (timestamptz, DEFAULT now())
- 索引: `param_key`

**server/src/modules/notifications/entities/notification.entity.ts**
- 表名: `notifications`
- 字段: `id` (bigint PK), `user_id` (bigint, FK → users, ON DELETE CASCADE), `type` (varchar 50, NOT NULL), `title` (varchar 200, NOT NULL), `content` (text, NOT NULL), `data` (JSONB, nullable), `is_read` (boolean, DEFAULT false), `sent_via` (varchar 20 数组, nullable), `region_code` (varchar 20, nullable), `created_at` (timestamptz, DEFAULT now())
- **P1 扩展字段**（发送状态追踪）：`send_status` (enum: 'pending' | 'succeeded' | 'failed', DEFAULT 'pending'), `sent_at` (timestamptz, nullable)。为第三方渠道（短信/推送）的运维、重试和监控提供数据基础。
- 索引: `(user_id, is_read, created_at)`, `(region_code)`。前瞻性说明：若后台需按类型全局查询，可后续添加 `(type, created_at)`；若需对 `sent_via` 数组做包含查询，可后续添加 `GIN(sent_via)` 索引。
- 关系: `@ManyToOne` → User

### Step 5: 创建 Migration 文件

**server/src/migrations/1716740000007-CreateFeedbackAndSystemTables.ts**

`up()` 方法按顺序执行：
1. 创建 ENUM 类型（幂等）：
   - `feedback_player_ratings_level_match_enum`
   - `feedback_player_ratings_sportsmanship_enum`
   - `feedback_player_ratings_action_cleanliness_enum`
   - `notifications_sent_via_enum`（或使用 varchar 数组，PostgreSQL 原生支持）
2. 创建 `feedbacks` 表（含 CHECK `overall_rating BETWEEN 1 AND 5`，UNIQUE `(match_id, player_id)`）
3. 创建 `feedback_player_ratings` 表
4. 创建 `system_params` 表（含 UNIQUE `param_key`）
5. 创建 `notifications` 表（`sent_via` 使用 `character varying(20)[]` 数组类型）
6. 添加外键约束
7. 创建索引

`down()` 方法严格反向执行：先 drop FK → drop index → drop table → drop ENUM。

**server/src/migrations/1716740000008-SeedSystemParams.ts**

`up()` 方法插入三条系统参数种子数据，使用 `ON CONFLICT (param_key) DO NOTHING` 保证幂等性。
`down()` 方法删除这三条记录。

**种子数据版本管理策略**：当前迁移仅负责初始化。未来对已有参数的变更需创建新的迁移文件（如 `1716740000009-UpdateAbilityWeights.ts`），使用 `UPDATE ... WHERE param_key = ?` 执行修改，禁止直接修改本种子迁移。

## 风险与注意事项

1. **PostgreSQL 数组类型**: `sent_via` 字段使用 `character varying(20)[]`，在 TypeORM 中通过 `type: 'varchar', array: true` 或 `type: 'simple-array'` 实现。考虑到项目使用原生 SQL Migration，Migration 中直接写 `character varying(20)[]`，实体中用 `@Column({ type: 'varchar', array: true, nullable: true })`。
2. **JSONB 类型**: `param_value` 和 `data` 使用 JSONB，TypeORM 中 `@Column({ type: 'jsonb' })`。
3. **CHECK 约束命名**: 遵循已有模式 `CHK_{table}_{description}`，如 `CHK_feedbacks_overall_rating`。
4. **外键删除策略**: feedbacks → matches 使用 `ON DELETE CASCADE`（比赛删除后反馈无意义），feedbacks → players 使用 `ON DELETE NO ACTION`（保留数据完整性）。
5. **Migration 顺序**: 1716740000007 必须在 1716740000006 之后，因为 feedbacks 依赖 matches 表。
