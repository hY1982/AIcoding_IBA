# 篮球匹配平台 — 面向非技术人员的集成测试Web仪表板

## Context

篮球匹配平台项目已完成 Phase 0（基础设施）和 Phase 1（数据层实体 + Migrations），共 18 个 TypeORM 实体、8 个迁移文件、26 个测试文件（覆盖率 97%）。但 Phase 2（Service 业务逻辑）、Phase 3（Controller/API 接口）、Phase 4（WebSocket）、Phase 5（前端业务页面）均尚未实现。

需求方（非技术人员）需要一种直观方式了解：
1. 当前项目哪些功能已完成、哪些待开发
2. 每个业务模块的测试场景和验收标准
3. 项目风险点和需特别关注的地方

因此需要在管理后台（`apps/admin`）中构建一个**可视化集成测试仪表板页面**，用业务语言展示所有测试场景、执行步骤、验收标准和风险识别。

## Recommended Approach

在 `apps/admin` 项目中新增 `/test-dashboard` 路由页面，采用**纯静态数据展示**架构（因后端 API 尚未实现），使用 Ant Design 组件构建可视化仪表板。

### 页面结构

```
TestDashboardPage（页面容器）
├── OverallProgress（总进度概览：模块数/已完成/待开发/风险点统计）
├── ModuleProgressGrid（模块完成度卡片网格，6大模块）
├── TestScenarioTable（测试场景列表：筛选、搜索、分页）
├── RiskAlertPanel（风险识别汇总面板）
└── TestScenarioDetail（抽屉式场景详情：步骤/数据/标准/风险）
```

### 核心设计决策

1. **纯静态数据**：测试场景数据硬编码在 `apps/admin/src/data/test-scenarios.ts`，不依赖后端 API
2. **状态标签体系**：
   - `completed`（绿色）— 数据层已实现
   - `testable`（蓝色）— 可基于数据层验证
   - `pending_dev`（灰色）— 待 Service/Controller 开发
   - `blocked`（红色）— 依赖其他未实现模块
3. **业务化描述**：所有场景用中文业务语言，如"球员A提交比赛意向后能否正确计算结束时间"
4. **Ant Design 组件**：Statistic、Progress、Card、Table、Tag、Drawer、Steps、Alert、Collapse

### 测试场景数据覆盖

按 6 大已完成模块分类，共 13+ 测试场景：

- **M1.1 用户与认证**（2场景）：注册加密存储、重复注册拒绝
- **M1.2 场地管理**（1场景）：场地创建与时段查询
- **M1.3 赛制管理**（1场景）：种子数据加载验证
- **M1.4 比赛意向**（3场景）：时间自动计算、提前1小时校验、多选限制
- **M1.5 比赛与群聊**（4场景）：匹配生成比赛、确认参赛+支付、人数不足失败、群聊消息
- **M1.6 反馈与系统参数**（2场景）：赛后反馈提交、系统参数动态生效
- **端到端**（2场景）：完整成功流程、匹配失败流程
