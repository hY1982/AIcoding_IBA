## 实现细节

### 加密方案（AES-256-GCM + 密钥版本管理）

```
密钥来源: process.env.ENCRYPTION_KEY (32字节，base64编码)
算法: AES-256-GCM
输出格式: v{version}:iv(16字节,hex):authTag(16字节,hex):ciphertext(hex)
示例: v1:a1b2c3...:d4e5f6...:7g8h9i...
```

- **密钥版本标识**: 密文前缀嵌入版本号（如 `v1:`），支持未来密钥轮换。解密时解析版本号，从密钥映射中选择对应密钥
- **密钥映射**: `ENCRYPTION_KEY` 为当前活跃密钥（v1），未来通过 `ENCRYPTION_KEY_V2` 等环境变量扩展
- 每次加密生成随机 IV，确保相同明文加密结果不同
- authTag 用于完整性校验
- 环境变量 `ENCRYPTION_KEY` 需添加到 `.env` 和 `.env.example`
- **密钥生成命令**: `openssl rand -base64 32`（记录在项目文档中）

### 实体设计要点

**User Entity:**
- `phone`: AES加密存储，使用 `@Column({ transformer: EncryptTransformer })`
- `phoneHash`: SHA-256 哈希（用于登录时等值查询索引，**不存储明文关联**）
- `passwordHash`: bcrypt 哈希（非加密，由 AuthService 处理）
- `realName`, `idCard`: AES加密存储（可选字段）
- `userType`: enum ('player' | 'venue_manager')
- `status`: enum ('active' | 'inactive' | 'banned')
- `regionCode`: 预留分区分片字段
- **索引**: `@Index(['phoneHash'])`（登录查询）、`@Index(['userType'])`、`@Index(['status'])`、`@Index(['regionCode'])`
- 关联: `player?: Player` (OneToOne), `venueManager?: VenueManager` (OneToOne)
- **反序列化优化**: Player/VenueManager 端使用 `@RelationId` 暴露 `playerId`/`venueManagerId`，减少循环依赖和序列化负载

**VenueManager Entity:**
- `userId`: BIGINT, UNIQUE, FK → users.id
- `companyName`, `contactName`, `contactPhone`
- 关联: `user: User` (OneToOne)

**Player Entity:**
- `userId`: BIGINT, UNIQUE, FK → users.id
- 基础属性: age, basketballAge, gender, height, weight, wingspan, standingReach, jumpingReach
- 计算能力值: `baseAbilityScore`, `matchAdjustValue`
- `totalAbilityScore`: `@Column({ generatedType: 'STORED', asExpression: 'base_ability_score + match_adjust_value' })` — 数据库层计算列，保证一致性
  - **架构决策**: 采用数据库计算列（性能强、一致性高），代价是规则变更需迁移。未来如需灵活调整，可在应用层增加虚拟 getter 作为备用路径
- **索引**: `@Index(['totalAbilityScore'])`（匹配查询）、`@Index(['regionCode'])`
- 关联: `user: User` (OneToOne), `positions: PlayerPosition[]` (OneToMany)
- **反序列化优化**: `userId` 通过 `@RelationId` 暴露，避免完整 User 对象序列化

**PlayerPosition Entity:**
- `playerId`: BIGINT, FK → players.id
- `position`: enum ('PG'|'SG'|'SF'|'PF'|'C')
- `priority`: INT, DEFAULT 1
- **复合唯一索引**: `@Index(['playerId', 'position'], { unique: true })`
- 关联: `player: Player` (ManyToOne)

## 测试数据库配置

实体测试将使用真实 PostgreSQL，配置如下：
- 测试数据库名: `basketball_platform_test`（与开发库分离）
- 连接参数: 复用 `.env` 中的 `DB_HOST/PORT/USERNAME/PASSWORD`，仅替换 `database`
- 测试生命周期:
  - `beforeAll`: 建立 DataSource 连接，`synchronize: true` 建表
  - `afterEach`: `TRUNCATE TABLE ... CASCADE` 清理数据（比逐条删除更快，保留表结构）
  - `afterAll`: 关闭连接
- **串行执行**: 实体测试使用 `jest --runInBand` 确保串行执行，避免并行冲突
- 实体测试中通过 `DataSource.query()` 查询 `information_schema.columns` 验证表结构
- **计算列集成测试**: 必须向真实 PG 插入记录后查询，断言 `totalAbilityScore` 严格等于两数之和

## 风险与注意事项

1. **ENCRYPTION_KEY 环境变量**: 需添加到 `.env` 和 `.env.example`，本地开发使用固定测试密钥
2. **TypeORM GENERATED 列**: PostgreSQL `GENERATED ALWAYS AS` 在 TypeORM 中通过 `@Column({ generatedType: 'STORED', asExpression: '...' })` 实现，需验证语法正确性
3. **实体关系循环引用**: User ↔ Player / User ↔ VenueManager 的 OneToOne 双向关联需注意导入顺序。缓解措施：非必要端使用 `@RelationId` 仅暴露外键ID
4. **测试数据库依赖**: 实体测试需本地 PostgreSQL 运行，测试数据库 `basketball_platform_test` 需提前创建或赋予创建权限
5. **加密字段查询限制**: `phone` 加密后无法直接等值查询，已通过 `phoneHash` 列解决。登录流程：用户输入手机号 → 计算 SHA-256 hash → 用 `phoneHash` 查索引 → 取出记录 → 解密 `phone` 验证
6. **计算列灵活性**: 采用数据库计算列（性能+一致性），代价是规则变更需迁移。已记录架构决策，未来可在应用层增加虚拟 getter 作为备用路径
